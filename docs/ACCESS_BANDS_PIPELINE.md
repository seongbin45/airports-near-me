# 시각대 배치 파이프라인과 지도 API 쿼터

2026-09-26 작성. 파이프라인 구조는 코드에서, 쿼터는 제공자 공식 문서에서 확인했다.
절차(체크리스트)는 `docs/ACCESS_BANDS_CHECKLIST.md`, 테이블 관계는 `docs/DATA_MODEL.md`.

## 1. 왜 시각대를 붙였나

카카오모빌리티 길찾기는 **출발 시각을 주지 않으면 호출 시점의 실시간 교통**으로 계산한다.
2026-09-25 전국 배치가 금요일 16~17시(KST)에 돌아 값에 퇴근길 정체가 섞였다
(수원 영통구 → 김포 137분). 그 값을 "평균 소요시간"으로 쓰면 사용자가 실제로 겪는 시간과 어긋난다.

그래서 행마다 어느 시각대 기준인지 남긴다(`access_times.depart_band`).

| `depart_band` | 출발 시각 (KST) | 뜻 |
|---|---|---|
| `any` | 지정 안 함 | 제공자가 **호출 시점**의 실시간 교통으로 계산. 컬럼 추가 전 행 전부 |
| `weekday_am` | 평일 08:00 | 그 시각의 예상 교통 |
| `weekday_day` | 평일 13:00 | 〃 |
| `weekday_pm` | 평일 18:00 | 〃 |
| `weekend` | 주말 13:00 | 〃 |

`any`를 지우지 않고 남기는 이유: 시각대 값을 못 구한 조합의 최후 fallback으로 쓰기 때문이다.
추천은 **정확히 맞는 시각대 → `any`** 순으로 찾고(`bandsForLookup`), `any`로 물러선 경우 화면이
그 사실을 표시한다(`accessBandMatched`).

## 2. 파이프라인 구조

```
[참조 데이터]                       [계획 — 순수 함수]              [실행]                [저장]
regions(lat/lng)  ──┐
  ↑ geocode-regions │    zone 같은 공항만           시각대별 출발 시각        access_times
airports(lat/lng) ──┼─→ planAccessTimes ─────────→  nextDepartureAt ──→ chain.run ──→ upsert
                    │    · 권역 다르면 제외(제주↔육지)      (KST 요일·시각)      (제공자)   (onConflict 4키)
access_times 기존 ──┘    · refresh-days 안이면 건너뜀                                    ↓
                         · limit까지 자름                                       [소비 — 런타임]
                                                                                trip.ts → recommend
                                                                                       ↓
                                                                                결과 카드 + doctor
```

### 2.1 계획 (`planAccessTimes`, 순수 함수 — 테스트 있음)

- `regionZone`/`airportZone`으로 **권역이 다르면 계산하지 않는다**(제주 구역 → 육지 공항은 육로가 없다).
  울릉군은 `ulleung` 권역으로 따로 뺀다.
- 시각대마다 슬롯을 하나씩 잡는다 — `(지역 × 공항 × 수단 × 시각대)`가 대상 조합 수다.
- 기존 행이 `is_sample = false`이고 `fetched_at`이 `refresh-days`(기본 30일) 안이면 건너뛴다.
  **이어받기가 되는 이유가 여기다** — 여러 회차로 나눠 돌려도 이미 받은 조합은 다시 계산하지 않는다.
- `limit`(기본 4000)까지만 자른다. 전국 4개 시각대는 1만 조합이 넘어 한 회차로 끝나지 않는다.

### 2.2 제공자 체인 — 출발 시각을 반영하는가가 기준

| 용도 | 체인 순서 | 출발 시각 반영 |
|---|---|---|
| 차량 (실시간, `any`) | 카카오모빌리티 길찾기 → TMAP → 네이버 → OSRM | ✗ |
| 차량 (시각대) | **카카오모빌리티 미래 길찾기** | ✓ (`supportsDepartureTime`) |
| 대중교통 (실시간) | ODsay | ✗ |
| 대중교통 (시각대) | **없음** | — |
| 좌표 | 카카오 → 네이버 → Nominatim | — |

- 시각대 배치는 **출발 시각을 실제로 반영하는 제공자만** 쓴다(`buildAccessTimeSources(…, { departuresOnly: true })`).
  실시간 전용 제공자(OSRM 등)의 값을 "평일 아침"으로 저장하면 컬럼이 거짓말을 하게 되기 때문이다.
- **그래서 대중교통 시각대는 만들 수 없다.** ODsay에 출발 시각 파라미터가 없어 계획에서 아예 빠진다.
- 오류 분류가 체인 동작을 정한다: `exhaust`(한도·키 거부·형식 변경)면 그 실행 동안 제공자를 빼고,
  `transient`는 1회 재시도 후 그 조합만 다음 제공자로, `nodata`는 "길 없음"으로 기록하고 다른 제공자에게 묻지 않는다
  (길찾기는 대개 결과가 같고, 지오코딩은 새 행정구역 이름이 한 곳에만 있을 수 있어 묻는다).
- 제공자마다 `minIntervalMs`를 두고 **다음 호출 시각을 미리 예약**(`nextSlot`)한다. 동시 4개로 돌려도
  OSRM·Nominatim 같은 공용 서버 정책(초당 1회)이 지켜진다(테스트 있음).

### 2.3 실행

- 동시성 `--concurrency`(기본 4), 연속 실패 `--max-fail`(기본 5) × 동시성만큼 실패하면 멈춘다.
- 100건마다 진행 줄을 찍는다: `… 200/4000 (1.4분) 저장 200 · 경로 없음 0 · 오류 0`.
- 저장은 **`(region_id, airport, mode, depart_band)` 키로 upsert** — 회차를 반복해도 같은 조합이 중복되지 않는다.
  `source`에 제공자 이름, `fetched_at`에 시각, `is_sample = false`를 함께 넣는다.
- 값을 못 구한 조합은 **추정값으로 채우지 않고 비워 둔다.** 다음 회차에서 다시 시도한다.

### 2.4 소비 (런타임)

`lib/server/trip.ts`가 여정의 날짜·출발 시각으로 시각대를 정하고(`bandFor` — 주말이면 시각과 무관하게
`weekend`, 평일은 10시 전 아침 / 17시 전 낮 / 그 뒤 저녁), `in('depart_band', bandsForLookup(band))`로
정확한 시각대와 `any`를 함께 읽어 **정확한 행을 우선**한다. 응답에 `accessBand`·`accessBandMatched`를 실어
결과 카드가 "○○ 기준 이동 시간이 아직 없어서 …" 경고를 띄우거나 타일에 시각대를 표시한다.

### 2.5 점검 (doctor)

| 게이트 | 판정 | 치명 |
|---|---|---|
| `access-times` | 실측 행이 1건 이상이고 지역이 채워짐 | ✓ |
| `regions-coords` | 유효 행정구역 전부에 좌표 | ✗ |
| `access-bands` | 실측 중 `any`가 아닌 행이 1건 이상 | ✗ |

`access-bands`가 `critical: false`인 이유: 값이 없으면 추천이 `any`로 물러서고 화면이 그 사실을
표시하므로 서비스는 계속 돈다. **그래서 종료 코드만 보면 놓친다 — 그 줄을 직접 봐야 한다.**

## 3. 쿼터

### 3.1 카카오모빌리티 — 길찾기 API 일일 제공량

| API | 일일 제공량 | 초과 시 단가 |
|---|---|---|
| 자동차 길찾기 | **10,000건** | 8원/건 |
| **미래 운행 정보 길찾기** | **5,000건** | 8원/건 |
| 다중 경유지 자동차 | 5,000건 | 16원/건 |
| 다중 출발지/목적지 | 1,000건 | 20원/건 |
| 길찾기 SDK | 100,000건 | 1원/건 |

[쿼터 및 가격 — Kakaomobility Developers](https://developers.kakaomobility.com/price/) (2026-09-26 확인).
일일 제공량은 변경될 수 있다고 명시돼 있다. **자동차 길찾기와 미래 운행 정보 길찾기는 별도 쿼터**라,
`any` 배치가 자동차 쿼터를 써도 시각대 배치의 5,000건은 줄지 않는다.

### 3.2 ODsay — 대중교통 API

| 서비스 유형 | 사용자 유형 | 제한 호출수 | 가격 |
|---|---|---|---|
| **Basic** | 개인 / 학생 / 5인 이하 스타트업 | **30 / 일** | 무료, 기간 제한 없음 |
| Standard | 제한 없음 | 100,000 / 일 | 가격문의 |
| Premium | 제한 없음 | 100,000 초과 / 일 | 가격문의 |
| Flex | 제한 없음 | 100,000 / 일 | 후불, **건당 25원** (VAT 별도) |

[운영정책 2. 호출 한도 제한](https://lab.odsay.com/doc/totalPolicy) · [구매문의](https://lab.odsay.com/contact/contact) (2026-09-26 확인).

함께 확인한 제약:

- **초당 호출 건수 제한이 서비스 유형별로 있지만 정확한 수치는 공개하지 않는다**(운영정책에 그렇게 명시).
  그래서 이 레포는 ODsay에 최소 간격을 걸지 않았다 — 알 수 없는 값에 추측을 넣지 않았다.
- 일일 제한 호출수를 넘기면 **이메일·문자로 통지**하고, 동의하지 않으면 서비스 일부 또는 전부가 제한될 수 있다.
- **Basic은 개인·학생·5인 이하 스타트업 전용**이다. 해당하지 않는 이용자가 Basic을 쓰면 발견 즉시 제한되고,
  부당 사용 기간·호출 수에 대한 비용을 청구한다.
- 대중교통 API의 기본 용도는 **출발-도착 경로 검색 같은 단일 호출**이고, 대규모 경로 검색은
  '대용량 대중교통 API'로 별도 문의해야 한다. **분석·연구 목적이나 대량 호출로 데이터를 쓰면
  사전 안내 없이 이용이 제한될 수 있다.**
- 일일 호출 수는 매일 자정에 초기화된다(개발자포럼 안내).

## 4. 이 레포에 주는 결론

### 4.1 차량 시각대 전국 배치 = 3일치

전국 대상 조합은 **14,176개**(도달 가능 3,544 × 시각대 4)이고, 한 회차는 기본 `--limit 4000`이다.
미래 운행 정보 길찾기가 **5,000건/일**이므로:

| 날 | 실행 | 누적 |
|---|---|---|
| 1일차 | `--limit 4000` | 4,000 |
| 2일차 | `--limit 5000` | 9,000 |
| 3일차 | `--limit 5000` | 14,000 |
| 4일차 | 남은 176건 | 14,176 |

- 급하면 **`--bands "weekday_am,weekday_pm"`**로 좁힌다 — 정체가 실제로 문제 되는 두 시각대만
  채우면 7,088건이라 2일이면 끝난다.
- 한도를 넘겨 호출이 나가면 **건당 8원**이 붙는다. 카카오디벨로퍼스에서 이 앱의 결제·유료 전환이
  켜져 있는지 확인한다. 꺼져 있으면 429로 멈추고, 켜져 있으면 과금된다.
- 한도(429)는 재시도로 풀리지 않으므로 그 실행 전체가 멈춘다 — **정상 동작이고 데이터 손상이 없다.**
  다음 날 같은 명령을 다시 돌리면 이어받는다.

### 4.2 대중교통 전국 배치는 Basic으로 불가능하다

- **30건/일**로는 전국 조합(수천 개)은커녕 한 지역의 공항 몇 곳도 못 채운다. 시각대는 더 말할 것 없다.
- 게다가 대량 호출 자체가 운영정책상 별도 계약 대상이다. 이 레포가 `npm run access-times -- --mode transit`으로
  전국을 훑는 설계는 Basic 약관과 맞지 않는다.
- **실사용자 트래픽도 30건/일이 상한**이라는 뜻이다. 추천을 받는 사용자가 하루 30명을 넘으면
  대중교통 결과가 비게 된다. 그래서 대중교통은 "키가 생기면 채운다"보다 강하게 봐야 한다 —
  **차량으로 대체할 수 없는 값이지만, 무료 유형으로 운영할 수 있는 값도 아니다.**
- 확인: 애플리케이션 **개요**에서 `현재 호출수 / 사용 가능한 제한 호출수`를, **통계**에서 호출·오류·평균응답속도를 본다.
  지금 내 키가 어느 유형인지 모르면 `--region 1 --limit 3 --dry`로 3건을 써 보고 개요의 호출수가 3으로 오르는지 확인한다.

### 4.3 그래서 무엇을 먼저 할 것인가

1. 차량 시각대 배치를 **`weekday_am`·`weekday_pm`부터** (7,088건 → 2일). 여기서 대부분의 사용자 체감이 해결된다.
2. 대중교통은 별개로 결정한다 — 유료 유형으로 갈지, 대중교통을 화면에서 "데이터 없음"으로 확정할지.
   **`--bands`에 대중교통을 섞어 돌리면 30건을 낭비하고 시각대도 못 얻는다.**
3. ODsay 키 인증(IP 등록)이 먼저 안 되면 위 판단은 못 한다 — 3건짜리 `--dry`로 성공/실패를 본다.
